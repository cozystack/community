# How the table can reach each reference

Supporting material for [README.md](./README.md), following [inventory.md](./inventory.md). The inventory answers *where* a reference lives; this answers *how a value computed from `_cluster.image-overrides` can get there*. Checked 2026-10-27 against the same tree.

## Why "the chart exposes a value" is not enough

The table is only known at install time, in the `cozystack-values` Secret. A value reaches a chart through these channels and no others:

| Channel | Can compute from the table | Reaches |
|---|---|---|
| A template of our own chart (wrapper or app) | yes, `.Values._cluster` is there | objects that template renders |
| The wrapper's `values.yaml` | no, it is static | subchart values |
| `tpl` inside a vendored template | only what the subchart context sees: its own values and `global`, **not** `_cluster` | the value it evaluates |
| `Package.spec.components.<c>.values`, rendered by the platform chart (`packages/core/platform/templates/bundles/*.yaml`, already used for cert-manager, gpu-operator, networking, linstor) | yes, the platform chart holds the table | top-level and subchart values of that package |
| HelmRelease values rendered by an app chart (tenant cluster addons in `packages/apps/kubernetes/templates/helmreleases/`) | yes | top-level and subchart values of that addon |
| `make update` patch of a vendored template | yes, if the table reaches the subchart: the platform chart sets it under the subchart's own key in the component values of that package | anything |

Subcharts see `global` but not `_cluster`. The wrapper cannot hand a subchart a computed value, so for vendored charts the choice is between the platform channel and a patch. `global` itself is not a usable channel for the table: it reaches every chart through `cozystack-values`, and rendering every chart with a `global.cozystack` key broke smee in bootbox, whose template reads `.Values.global.rbac.type` whenever `global` is non-empty.

## Per chart

`OURS` means the reference renders from a Cozystack template, so a cozy-lib call there is enough. `VENDORED` means it renders from an upstream template.

| Chart | Reference | Source | Value | `tpl` | Route |
|---|---|---|---|---|---|
| apps: postgres, mariadb, mongodb, rabbitmq, redis, valkey, foundationdb, kubernetes; system: harbor, keycloak, monitoring, seaweedfs-db | CR image fields | OURS | — | — | helper in the template |
| etcd-operator | `OPERATOR_IMAGE` env (its own image, run by snapshot and restore pods) | OURS | `image.*` | — | helper in the template, same value as the container |
| etcd | the etcd image itself | operator, from `--etcd-image-repository` / `ETCD_IMAGE_REPOSITORY` (default `quay.io/coreos/etcd`) plus `v<spec.version>` | no field in `EtcdCluster` or `EtcdMember`; the operator-wide repository | — | helper in our etcd-operator template sets `ETCD_IMAGE_REPOSITORY` when the table renames the image (confirmed on a cluster); tag and digest need `spec.image` in `cozystack/etcd-operator` |
| capi-providers-* | gzip in ConfigMap | OURS | provider `imageUrl` | — | helper in `providers.yaml`; where the default lives only in the archive, `imageUrl` only when the table changes it |
| kubevirt-cdi-operator, kubevirt-operator, forklift-operator | operator env literals | OURS, generated by `make update` | none | — | `make update` emits helper calls; for KubeVirt it replaces `VIRT_OPERATOR_IMAGE` with a helper that adds a component's variable only when the table changes it or the operator (confirmed on a cluster) |
| cert-manager | `--acme-http01-solver-image` | VENDORED | `acmesolver.image.*` (parts, digest supported) | no | platform channel through `cozy-lib.imageOverrideValues`; tenant clusters through the `kubernetes` app addon with the same helper (both confirmed on a cluster) |
| bootbox (smee) | `tink_worker_image=` in env | VENDORED | `tinkWorkerImage` (whole) | no | platform channel, needs the default reference to apply `newTag`/`newName` alone; or patch |
| gpu-operator | `ClusterPolicy` 19 triples, `DRIVER_MANAGER_IMAGE` env | VENDORED | per-component `repository`/`image`/`version`; v26.3.1 builds `repository/image@version` when `version` starts with `sha256:`, and takes `image` alone as a whole reference when `repository` and `version` are empty; CR fields win over the operator env, so `DRIVER_MANAGER_IMAGE` is a fallback | no; `ClusterPolicy` cannot be switched off | patch: `clusterpolicy.yaml` and `nvidiadriver.yaml` render with a copy of the values whose triples the table changes are rewritten, so `match` applies and new components need no patch change; the platform channel and the tenant addon pass the table under the subchart's key |
| kafka-operator (strimzi) | operator env, `STRIMZI_KAFKA_IMAGES` per version | VENDORED | `defaultImageRegistry`, `defaultImageRepository`, `defaultImageTag`, per-component `<key>.image.{registry,repository,name,tag,tagPrefix,digest}`; one `tag`/`digest` per key for every Kafka version | no | patch: every reference comes from the `strimzi.image` template, which the patch passes through the helper, so each Kafka version takes its own entry (confirmed on a cluster) and our `Kafka` CR needs no image |
| kamaji | `--migrate-image` | **our wrapper `values.yaml`**, static string | `extraArgs` (whole) | no | platform channel with the default reference duplicated, or patch. Same image as the container |
| kube-ovn | `--image`, NAT gateway ConfigMap | VENDORED | `global.registry.address`, `global.images.*` (parts, one registry for all images) | no | patch of the two templates through the helper (confirmed on a cluster); the containers stay with the post-renderer |
| local-storage (openebs) | `OPENEBS_IO_HELPER_IMAGE` | VENDORED | `helperPod.image.*` (parts) | no | platform channel |
| mariadb-operator | `RELATED_IMAGE_*`, `MARIADB_OPERATOR_IMAGE` | VENDORED | `config.*Image` (whole), `mariadbImageName` (name only), `MARIADB_OPERATOR_IMAGE` built by the upstream `image` template | no | patch: whole references through the helper, the name-only field through a helper that applies only `newName`, and the operator's own image |
| piraeus-operator | `image-config` ConfigMap | VENDORED | `imageConfigOverride`: overlays of `base` plus `components.<name>.{image,tag,digest}` and per-OS `match` rules; `RELATED_IMAGE_<component>_<image>` (or `RELATED_IMAGE_<component>`) env takes a whole reference first | no | patch of the operator Deployment: a `RELATED_IMAGE_<component>_<image>` variable for each image the table changes, defaults read from the upstream `config/manager` files kept beside the chart (confirmed on a cluster) |
| linstor | LinstorCluster/Satellite `podTemplate.containers[].image` | OURS | — | — | already covered by the post-renderer (a `containers` field) |
| postgres-operator (CNPG) | `OPERATOR_IMAGE_NAME` env | VENDORED | `image.repository`, `image.tag` (same as the container) | `additionalEnv` is `tpl`'d, but in subchart context | platform channel; setting `image.*` fixes container and env together |
| postgres-operator (barman) | `SIDECAR_IMAGE` | VENDORED | `sidecarImage.*` (parts) | no | platform channel |
| victoria-metrics-operator | defaults the operator picks | VENDORED operator, OURS CRs | operator `env` (static, no `tpl`), `envFrom`; CR `image.{repository,tag}` on every component, `configReloaderImage` on VMAgent, VMAlert, VMAlertmanager, VMAuth | no | helper in our CRs, the field set only when the table changes the image (confirmed for VMAgent) |
| opensearch | defaults the operator picks | OURS CR | `general.image`, `initHelper.image`, `dashboards.image` | — | helper in the CR |
| redis, valkey sentinel | operator default | OURS CR | `sentinel.image` | — | helper in the CR |
| foundationdb cluster and backup | operator builds the image from `version` and `imageType` | OURS CRs; the backup driver creates its own `FoundationDBBackup` | `mainContainer.imageConfigs`, `sidecarContainer.imageConfigs`: items of `baseImage`, `tag`, `tagSuffix`, `version` | — | helper in the CRs, one item for the cluster's version, only when the table changes it; the backup driver reads the table through `pkg/imageoverrides`; `tag` may carry `@sha256:` (confirmed on a cluster) |
| Kamaji control plane and addons | Kamaji builds images from `version` | OURS CR (`KamajiControlPlane`) | `registry`; `containerImageName` of apiServer, controllerManager, scheduler; `addons.konnectivity.{agent,server}.image` (defaults in the CRD schema inside the cpprovider archive); `addons.coreDNS`, `addons.kubeProxy` `imageRepository`/`imageTag` | — | helper in the CR; tags follow `version`, digests not reachable |
