# 0003. A Bucket account's keys come from its BucketAccess, which cozystack-controller re-creates on a mint and deletes on a revoke

- **Date:** `2026-11-23`
- **Status:** Accepted
- **Deciders:** `@kvaps`
- **Proposal:** [`../README.md`](../README.md)

- **Decided in:** [`cozystack/community#138`](https://github.com/cozystack/community/pull/138), [`cozystack/cozystack#5383`](https://github.com/cozystack/cozystack/pull/5383)
- **Implemented in:** [`cozystack/cozystack#5383`](https://github.com/cozystack/cozystack/pull/5383)

## Context

[0002](0002-account-list-comes-from-chart-rendered-credential-templates.md) has the platform choose every secret: the API or the controller generates a password, stores it in the account Secret in one of four formats, and the engine's operator consumes it. A Bucket user's keys break that assumption. The Bucket chart can render its accounts like any other chart, one per user. What is new is that the platform does not choose the secret: the engine issues it.

A Bucket user's keys come from the COSI driver. The chart renders one `BucketAccess` per user. The COSI sidecar asks the SeaweedFS driver to grant access for an account named after the BucketAccess UID, and the driver generates a random access key and secret key (seaweedfs-cosi-driver `v0.5.0`, `pkg/driver/provisioner.go:303-304`). The sidecar writes them once, as a `BucketInfo` JSON document, into the Secret the BucketAccess names, and it never grants again or rewrites that Secret (COSI `v0.2.2`, `sidecar/pkg/bucketaccess/bucketaccess_controller.go:77-80, 244-273`). Nothing passes caller-chosen keys to the driver: its only parameters come from the cluster-scoped BucketAccessClass, and the COSI API has grant and revoke but no rotate. Before this change `bucket-system` copied the keys into `<release>-<user>-credentials` behind a `lookup`, and every tenant with `use` access could read them.

## Decision

A template that names a BucketAccess in the new optional field `spec.bucketAccess` (`name`, `bucketClaimName`, `bucketAccessClassName`) is engine-issued, whatever else it says. Its keys are stored as the driver issues them, so its format is `plaintext`, and a CEL rule on the CRD refuses `bucketAccess` with any other format. `format` keeps one meaning across the API, how a secret is stored, and `bucketAccess` says who issues it. The Bucket chart renders such a template per tenant user and no longer renders that user's BucketAccess.

cozystack-controller runs a separate reconciler for templates that name a BucketAccess. It creates the BucketAccess and owns it, waits for the grant, and copies the keys into the account Secret `<template>.account`: the access key under `accessKeyID`, the secret key under `password`, `username` set to the account name, and an annotation naming the BucketAccess, which marks the Secret as engine-issued. No tenant role selects or grants that Secret. The reconciler for the platform-chosen passwords skips these templates and is otherwise unchanged.

A mint or a revoke still writes one object: the account Secret, rebuilt from the template without keys and carrying a random request id. The controller sees a request the current BucketAccess was not created for. It deletes that BucketAccess, which makes the sidecar revoke the old identity. For a mint it then creates a new one tagged with the request id and copies the new keys into the Secret, marked as serving that request. For a revoke it creates none: once the old BucketAccess is gone it marks the Secret as serving the revoke, and the account holds no keys until the next mint, so a revoke locks the user out. The API waits a bounded time (60 seconds by default, set by a flag of cozystack-api) for the Secret to be marked with its request id. A mint then returns the keys once: the secret key in `password`, and the access key in one new optional field, `CredentialRequestStatus.accessKeyID`. A revoke returns no keys. On timeout the API answers a retryable error and returns nothing; the controller still serves the request, and the next mint or revoke supersedes it. For an engine-issued template only, the API reads that one Secret, uncached, after writing it.

While the template lives, the controller deletes a BucketAccess only once the sidecar has put its finalizer on it. The sidecar has the driver grant an identity, writes the Secret, and only then adds the finalizer (COSI `v0.2.2`, `sidecar/pkg/bucketaccess/bucketaccess_controller.go:179-295`); a delete before that point skips the driver revoke and leaves the identity, with working keys, behind. A request that arrives during a grant waits for it. The template's status mirrors the account Secret as the latest request left it, granted or not, so a request that never completes does not leave every following one in conflict. A lost account Secret is written again from the live grant rather than re-granted, so it does not rotate keys under the clients that hold them. A change of the template's BucketAccess class, after a change of the user's `readonly` flag or of the bucket's `storagePool`, is recorded as a revoke by cozystack-controller: the old grant goes, none replaces it, and the next mint is granted under the new class.

A user marked `platform: true` is a platform account and gets no template. It keeps its chart-rendered BucketAccess, and its keys stay in `<release>-<user>-credentials`, which is labelled `internal.cozystack.io/tenantresource: "false"` and not selected by the ApplicationDefinition; its keys are never minted. backupstrategy-controller sets the flag on the `system` user of the bucket it provisions for default backups, `cozy-backups`. The field sits in the tenant schema of every Bucket, so whoever can edit the Bucket can set or clear it. Setting it on a tenant user takes the account out of the credentials API: its template goes, and the chart renders the user's BucketAccess itself, which is a re-grant (Consequences). Clearing it drops the chart-rendered BucketAccess, which carries no keep annotation, so the driver revokes those keys, and the user becomes a normal account: the controller grants it new keys that nobody is shown, and a mint issues working keys to its caller. On the `system` user of `cozy-backups` that revokes the keys the platform's default backups read, until backupstrategy-controller sets the flag again. It gives nobody a privilege they lacked, since whoever can edit the Bucket can delete it. For a tenant user, `<release>-<user>-credentials` keeps only `endpoint` and `bucketName`, which are not secret.

The conversion marks each existing tenant BucketAccess `helm.sh/resource-policy: keep` and `credentials.cozystack.io/adopt: "true"` before any chart changes version. When the chart stops rendering a BucketAccess, Helm therefore leaves it in place, and the controller adopts it and copies the keys it already has. Clients keep working until the first mint. The conversion also strips `accessKey` and `secretKey` from each tenant user's `<release>-<user>-credentials`: Helm's three-way patch cannot remove a key the old manifest set through `stringData`, so the chart switch alone would leave them readable.

## Why not the alternatives

- **A format of its own, `cosi`, with `bucketAccess` set exactly when the format is `cosi`.** It was this record's first version. It lost because `cosi` encodes nothing: `Known` and `Encode` refuse it, and the keys end up stored in plaintext anyway. The name says who issues the secret, which `bucketAccess` already says on its own, so `format` would stop meaning one thing across the API, and the name would also have to be reserved against a registered `CredentialFormat`. Raised by lexfrei on [`cozystack/community#138`](https://github.com/cozystack/community/pull/138).
- **Keep a stable access key and mint only the secret key, writing the identity straight into the SeaweedFS IAM.** It fits the API as it is, with one value per mint. But it needs an engine-specific writer racing the driver's own read-modify-write of `identity.json` and the per-identity files (`provisioner.go:321-327, 376-389`) across namespaces, and it takes user keys out of COSI.
- **Copy the driver's keys into the account Secret and offer no mint.** It hides the keys but still needs a copy-from-a-foreign-Secret mode, and a leaked key could then only be replaced by deleting the user.
- **Keep the BucketAccess in the chart and have the controller only re-create it.** It needs no ownership transfer, but a Helm upgrade during a mint re-creates the BucketAccess under the controller, and the conversion would still need a separate copy path for existing keys.

## Consequences

- Every mint rotates both keys and kills the previous pair. A client that read the keys from `<release>-<user>-credentials` loses them at the conversion and has to mint.
- A mint takes as long as a COSI grant, usually seconds. Under a slow driver a caller can be answered with a timeout and has to mint again. A revoke takes as long as a COSI revoke, and longer when it lands during a grant, which it waits out.
- A BucketAccess the sidecar never finalizes, because its grant keeps failing, blocks mints and revokes on that account until it completes or an administrator removes it after checking the driver for an identity it left.
- The cleanup of a deleted template and the garbage collection through its owner reference delete the BucketAccess without the finalizer check, so a template removed inside the grant window can leave an identity, with working keys, behind. Closing that would take a finalizer on the template.
- A Secret restored from an older backup carries an older request id, and the controller serves it as a new request: the keys rotate.
- The API reads one Secret for engine-issued templates. cozystack-controller gains create and delete on `bucketaccesses`.
- A change of `users.<name>.readonly` or of `storagePool` gives the template another BucketAccess class, and the controller records it as a revoke of its own: the account Secret loses its keys, the record shows `Revoked` by cozystack-controller with a history entry, the old BucketAccess is deleted, and none replaces it. The class change takes effect with the next mint, which the tenant needs anyway to get working keys, so no grant ever holds keys nobody was shown. A mint already pending when the class changes is served under the new class.
- A user moved between tenant and platform is a re-grant. Helm cannot take back a BucketAccess the controller created.
- `publicRead` has no keys and stays chart-rendered.
- The conversion needs no finish Job and leaves no standing identity: it strips the tenant-readable keys itself, and the COSI Secret has to stay for the grant.

## Revisit if

COSI gains a rotate call or caller-supplied keys, which would let a mint keep the BucketAccess. Also revisit if a second engine issues its own secrets: then `bucketAccess` should give way to a general reference to the issuer, still beside `format`.
