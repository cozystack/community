# Kairos as a second worker OS for tenant Kubernetes pools

- **Title:** `Kairos as a second worker OS for tenant Kubernetes pools, selected through a hoster-side NodeGroupClass`
- **Author(s):** `@lexfrei`

## Overview

I propose that a `KubernetesNodes` pool can run Kairos workers next to Talos ones. A Kairos worker boots an immutable disk image built from an OCI image and joins the tenant control plane with `kubeadm join` through the Kairos Cluster API bootstrap provider.

Everything OS-specific moves off the pool into a new cluster-scoped, hoster-owned, immutable `NodeGroupClass`, in the way a PVC names a `StorageClass`, for Talos as well as for Kairos. A pool names a class and keeps only the fields that mean the same thing on every OS. The platform ships two classes, `talos` and `kairos`, and a hoster adds classes for its own images and Talos settings. Existing pools move onto Talos classes without rolling.

The reason for a second OS is narrow: a hoster who needs a kernel module or a driver that the platform does not ship can add it to a Kairos worker image with one `FROM` layer on a platform image, while on Talos the same module means building and hosting a custom Talos image for every Talos release. Everything else in this proposal is about making that option cost as little as possible for the platform and for pools that never use it.

## Scope and related proposals

- **Builds on [`kubernetes-nodes-split`](../kubernetes-nodes-split/).** One pool per `KubernetesNodes` HelmRelease stays as it is. This proposal adds a second bootstrap path to that chart and a class the pool points at.
- **Labels and taints** follow [cozystack/community#103](https://github.com/cozystack/community/pull/103), under review as decision 0001 of `kubernetes-nodes-split`: one field set that both OS paths render. This proposal follows it, and a change there applies here.
- **GPUs.** This proposal includes the Kairos GPU guest that [cozystack/community#101](https://github.com/cozystack/community/pull/101) proposed: the image recipe, its `test` stage and the gpu-operator contract, in [section 10](#10-gpu-guest-on-kairos). GPU classes, the GPU mode and license delivery belong to [#99](https://github.com/cozystack/community/pull/99) (`gpudevice`), and the vGPU licensing model for virtual machines to [#100](https://github.com/cozystack/community/pull/100). A pool's `gpus` field is whatever `gpudevice` defines, and this proposal adds no GPU field to the pool or the class.
- **Deferred to future proposals:** one golden image catalog shared by virtual machines and workers, with goldens found by a label in `cozy-public`; worker pools as N virtual machines from a VM template shared with `vm-instance`, plus a bootstrap config; an OS-neutral join contract published once per tenant cluster. This proposal does not depend on them and is written so that each can land later without undoing it.
- **Implementation**, all draft or open on 2026-10-23: [cozystack/cozystack#4902](https://github.com/cozystack/cozystack/pull/4902) (Cluster API v1.13.7, a prerequisite), [#4911](https://github.com/cozystack/cozystack/pull/4911) (Kairos pools), [#4927](https://github.com/cozystack/cozystack/pull/4927) (labels and taints), [#4949](https://github.com/cozystack/cozystack/pull/4949) (scale from zero). [Rollout](#rollout) lists what changes in #4911 before it merges.

## Context

### What a pool is today

A `KubernetesNodes` pool renders a `MachineDeployment`, a machine template for its substrate (`KubevirtMachineTemplate` or `ProxmoxMachineTemplate`), a `MachineHealthCheck` and a `WorkloadMonitor`, and its `talos-reconcile` Job produces the `TalosConfigTemplate` (`packages/apps/kubernetes-nodes/`). The tenant cluster has one cluster-autoscaler (`packages/apps/kubernetes/templates/cluster-autoscaler/`), and each pool carries its autoscaler settings as annotations on its `MachineDeployment`. Workers are Talos (`talos.version: v1.13.6` in that chart's `values.yaml` on main), bootstrapped by CABPT, with `talos-csr-signer` next to the Kamaji control plane. On KubeVirt the worker disk comes either from the Talos Image Factory over HTTP or, with `osImage.builtin`, as a CDI clone of a golden DataVolume that `packages/system/kubernetes-worker-image` imports once into `cozy-public`. On Proxmox it is a clone of a Talos VM template selected by `proxmox.templateTags`.

The pool carries its Talos settings itself: `talos.*` (version, schematic, Image Factory URLs and CA, registry mirrors), `osImage`, `kernelModules` and `proxmox.templateTags`. Any second OS added the same way would add its own pool fields beside them, and the chart would have to refuse or ignore each OS's fields on the other's pools.

`kubernetes-nodes-split` set the goal that workers are uniformly Talos and that no kubeadm path remains. This proposal brings a kubeadm join back, for opt-in pools only. Talos stays the path every existing pool takes.

### What a Kairos worker is

The draft in cozystack/cozystack#4911 builds one worker image per supported Kubernetes minor from `packages/apps/kubernetes-nodes/images/kairos-worker`:

- the OS base is Hadron v0.5.3, a musl-based Kairos distribution;
- kubelet is built from source with `CGO_ENABLED=0`, because the upstream release kubelet is linked against glibc and does not start on musl; kubeadm is the static upstream release binary;
- containerd 2.2.9, runc v1.5.2 and CNI plugins v1.9.1 are fetched with checksum verification;
- a `test` build stage refuses a dynamically linked kubelet or kubeadm and checks that both report the expected version.

AuroraBoot v0.27.1 turns the image into a raw EFI disk, which is converted to a compressed qcow2 and put into a container disk for CDI (`images/kairos-worker-disk`). The OS image the disk is made from is published too, see [The worker image](#5-the-worker-image). The disk `.tag` files pin the published disks by digest: `ghcr.io/cozystack/cozystack/kairos-worker-v1.31` to `kairos-worker-v1.35`. The v1.35 disk is one gzip layer of about 381 MB.

The pool joins through `KairosConfig` with `distribution: kubeadm`, from [kairos-io/cluster-api-provider-kairos](https://github.com/kairos-io/cluster-api-provider-kairos). The provider mints the join token, cross-checks the CA in the `<cluster>-kubeconfig` Secret against the `<cluster>-ca` Secret, and writes the kubelet `providerID`; the join script it renders refuses the join on the node when kubeadm's version differs from the Machine's by even a patch.

### The problem

A hoster sometimes needs a kernel module or a driver in the worker that the platform does not ship: a vendor guest driver, an out-of-tree storage or network module, or a module built with options the stock one lacks. The first concrete case is the NVIDIA vGPU guest driver, which has no Talos extension.

On Talos the supported way to add a module is a system extension, selected through an Image Factory schematic (`talos.schematicID`). Extensions that Sidero Labs publishes are available that way. A module outside that catalog has to be built as an extension against the exact kernel of a Talos release, and the hoster then runs its own image build or image factory to get an installer and a disk that carry it. Since Talos 1.12 the kernel command line includes `module.sig_enforce=1` (`pkg/machinery/kernel/kernel.go` and the `minTalosVersionDisableModSigVerify` quirk in `pkg/machinery/imager/quirks/quirks.go` in siderolabs/talos), and the kernel signs its modules with a key from its own build (`CONFIG_MODULE_SIG_ALL` in the siderolabs/pkgs kernel config), so the extension also has to come out of that build or the image has to drop the argument. Every Talos release repeats this work.

A Kairos worker image is an ordinary OCI image. With the platform's OS image published (see [The worker image](#5-the-worker-image)), a hoster adds a module or a driver in a `FROM` layer on top of it, builds a disk with the same recipe, and points a class at it. The hoster rebuilds when the platform image moves, but uses only a container build to do it.

A second, smaller reason: a kubeadm join is the reference worker join for Cluster API. A Kairos pool does not need `talos-csr-signer` or a Talos machine config, so a fault in either does not reach it.

## Goals

- The class is the whole OS boundary, for Talos and Kairos alike. A pool names a class and keeps only fields that are not specific to one OS family: scaling, health checks, `cluster`, `version`, `roles`, labels and taints, `kubelet`, the VM shape and `gpus`. `sshKeys` is the one new pool field besides `nodeGroupClassName`, and it acts on one OS only, see [section 2](#2-the-pool-after-the-move).
- Adding an OS adds a class and a bootstrap path, and no OS-specific pool field.
- Existing pools move onto Talos classes without rolling: the move itself rolls no pool, because every pool renders as the same release renders it from the old pool fields.
- Kairos pools have the same lifecycle contract as Talos pools: MachineHealthCheck, autoscaling including scale from zero, labels and taints, rollout on every change.
- A hoster can supply its own worker image, and a hoster image does not break when a Cozystack upgrade moves the Kubernetes patch the platform pins.
- `gpus` entries pass through to the VM the same way on every OS, and whether the guest can use them depends on the image, apart from the refusal `gpudevice` applies to vGPU classes on Talos pools.
- At general availability Cozystack carries no downstream patches to the Kairos provider code.

### Non-goals

- **The OS of management-cluster hosts.** Kairos as a host OS for the management cluster is a separate decision with a different blast radius, and nothing here depends on it. This proposal covers tenant worker VMs only.
- **GPU classes, the GPU mode and license delivery.** `gpudevice` (#99) defines them, for virtual machines and workers alike; the vGPU licensing model for virtual machines is #100.
- **Kairos control planes.** Tenant control planes stay on Kamaji. The provider's `KairosControlPlane` (k0s, k3s) is not used. A kubeadm control plane on Kairos is not supported by the provider today; upstream treats it as a separate design ([kairos-io/kairos#4920](https://github.com/kairos-io/kairos/issues/4920), closed 2026-10-22).
- **Kairos on Proxmox in this rollout.** [Section 3](#3-substrate-and-os) lists what it would need.
- **In-place OS upgrades.** Workers are replaced, never upgraded with `kairos-agent upgrade`.
- **The deferred proposals** listed in [Scope](#scope-and-related-proposals): a shared golden catalog, workers as VMs from a shared template, a join contract.

## Design

### 1. `NodeGroupClass`

A cluster-scoped resource in `cozystack.io/v1alpha1`. It does not get a group of its own: it sits in the same group as `SchedulingClass`, the existing cluster-scoped class that a hoster creates and a tenant names to place its workloads. Only the hoster creates classes: the tenant chart (`packages/apps/tenant`) grants tenant roles through RoleBindings only, so a tenant has no way to create a cluster-scoped object.

```yaml
apiVersion: cozystack.io/v1alpha1
kind: NodeGroupClass
metadata:
  name: kairos-example-v1.35.6-r1
spec:
  bootstrap: kairos         # talos | kairos
  image:                    # optional; omitted = the platform image for the pool's version
    kubernetesVersion: v1.35.6
    reference: registry.example.com/workers/kairos-worker@sha256:0123...
---
apiVersion: cozystack.io/v1alpha1
kind: NodeGroupClass
metadata:
  name: talos-example-nvme-r1
spec:
  bootstrap: talos
  talos:                    # the fields the pool carries today under talos.*
    version: v1.13.6
    schematicID: 0123...
  kernelModules:
    - name: nvme_tcp
  substrates:               # image source per substrate; the pool's substrate picks one
    kubevirt:
      osImage:
        factory: {}
    proxmox:
      templateTags: [talos-v1.13.6]
```

- `spec` is immutable as a whole, enforced by a CEL rule (`self == oldSelf`). A new image or version is a new class with a new name, so no edit can roll every pool that uses a class at once.
- `bootstrap` names the bootstrap family: `talos` (CABPT and a `TalosConfigTemplate`) or `kairos` (the Kairos provider with `distribution: kubeadm` and a `KairosConfigTemplate`). A later family, such as plain kubeadm on a cloud image, is a new value. It is the only OS choice; the pool has none.
- A Talos class carries everything the pool carries under `talos.*` today, plus `kernelModules`, and the image source for each substrate: `osImage` for KubeVirt, `templateTags` for Proxmox. One class can serve pools on either substrate, because the class is the OS boundary and the substrate stays a property of the pool. A Talos class without `substrates.kubevirt` boots KubeVirt pools from the Image Factory with the class's own `talos.*` settings, as a pool without `osImage` does today; a Talos class without `substrates.proxmox` has no Proxmox entry. The built-in `talos` class has no Proxmox entry, because `templateTags` has no default, so a new Proxmox pool names a hoster class. An unset field in a Talos class takes the chart's default.
- `image` is allowed only with `bootstrap: kairos`, and `talos`, `kernelModules` and `substrates` only with `bootstrap: talos`, enforced by CEL. `image.kubernetesVersion` and `image.reference` are both required when `image` is set. `reference` must be pinned by digest, enforced by CEL, so a push to the same tag cannot change what a class boots. The Machine `version` of a pool on that class comes from `kubernetesVersion`, not from the chart's `files/versions.yaml`.
- The platform ships two classes: `talos`, which stands for the chart's Talos defaults, and `kairos`, without `image`, which stands for the platform's image for the pool's Kubernetes version. Their content does not change between releases, while what they resolve to follows the platform, as pools without stored Talos values do today.
- The class carries the OS-specific settings and the image only. GPU settings, licenses and Secret references stay off it.

The names `talos` and `kairos` are built in: the chart resolves them without reading any object, so a pool on them does not depend on the class existing, and an upgrade that renders a pool before the platform has created the class objects, or a deleted `talos` class, changes nothing for it. The two objects exist so that the classes can be listed, and an admission rule refuses creating or replacing a class named `talos` or `kairos` with any other `spec`; metadata such as a default-class annotation (open question 4) is not compared, so a hoster cannot create a `talos` or `kairos` object whose content the chart would silently ignore.

For any other name the chart reads the class with `lookup` at render time, as it already reads the parent `KamajiControlPlane`. A missing class fails the render with a message naming it. A class deleted while pools use it fails their next render. The objects already in the cluster stay, so existing Machines keep running and the autoscaler can still scale the pool from its current templates; a change to the pool or a chart upgrade fails until the class is back. Refusing that deletion is an open question.

### 2. The pool after the move

A pool gets `nodeGroupClassName` and `sshKeys` and loses every OS-specific field. It keeps:

- scaling: `minReplicas`, `maxReplicas`, `maxNodeProvisionTime`;
- health checks: `maxUnhealthy`, `nodeStartupTimeout`, `readyUnknownTimeout`, `readyFalseTimeout`;
- `version`, `roles`, `labels` and `taints`, `kubelet`;
- `cluster`, the parent `Kubernetes` object;
- the VM shape: `substrate`, `instanceType` or `resources`, `podCpuLimit` and `podCpuRequest`, `diskSize`, `storageClass`, the substrate-specific placement settings including `proxmox.dnsServers`, `logSerialConsole`;
- `gpus`, as `gpudevice` defines it.

`talos.*`, `osImage`, `kernelModules` and `proxmox.templateTags` move into Talos classes ([Upgrade and rollback compatibility](#upgrade-and-rollback-compatibility) describes the migration). A Kairos pool therefore has no Talos field to refuse or ignore, and a Talos pool has no Kairos field apart from `sshKeys`, which is VM-level.

`sshKeys` is new on the pool: a VM-level setting with the same name and shape as on `vm-instance`, rather than a field of one OS. On a Kairos pool the chart passes the key to the provider's `sshPublicKey` field, which in provider v0.2.1 holds a single key, so a Kairos pool with more than one key in `sshKeys` fails the render with a message that says so, rather than dropping keys. Accepting a list of keys there is an upstream change and the next step. Talos runs no SSH server, so on a Talos pool the field has no effect, and its description says so. When workers become VMs from a template shared with `vm-instance`, the field goes with the rest of the VM shape.

`gpus` entries pass through to the VM template unchanged on every OS, on the KubeVirt substrate. Admission from `gpudevice` refuses a vGPU class on a Talos pool, because Talos workers carry no vGPU guest driver. It has to tell a Talos pool by the `bootstrap` of the pool's class, and the built-in `talos` and `kairos` by name, since they resolve without an object. Otherwise whether the guest can use the device is a property of the image: the platform `kairos` image carries no GPU driver, a hoster image built by [section 10](#10-gpu-guest-on-kairos) does, and a Talos image carries what its schematic adds. The chart does not check the image. On Talos `gpus` also reaches the machine config: when a Talos class leaves `kernelModules` unset, a pool with an `nvidia.com/*` GPU gets `nvidia`, `nvidia_uvm`, `nvidia_drm` and `nvidia_modeset`, as the pool's `kernelModules` default does today. Three pool fields shape what a class renders: `version` picks the platform image and the Machine version of a Kairos class without `image`, `substrate` picks the class's entry, and `gpus` picks the Talos kernel modules a class leaves unset. Today the chart recognises a GPU by the `nvidia.com/` prefix of an entry's `name`; a `gpudevice` class entry has a `className` instead, so the rule has to resolve the GPU class and check the resource name of its device-plugin source, and the move to class entries keeps the modules a pool gets unchanged.

**The default class.** A pool created without a class gets the cluster's default written into its `nodeGroupClassName` once, at creation, as a PVC gets `storageClassName`. The chart never computes a default at render time, so changing the default later changes no existing pool. The Cozystack API writes it when it creates the pool, before the validating admission chain runs, so admission already sees the class, reading the cluster's default from the source open question 4 settles. This is the first default the API persists: its existing defaulting (`applySpecDefaults`) runs on read only. On an update that omits the field, the API puts the stored value back before validating admission too, so a full replace with a manifest written before the field existed does not remove the class. An OpenAPI or kubebuilder default on the field would be static rather than the cluster's default, so it is not used, and the `+kubebuilder:default` #4911 sets is removed in [Rollout](#rollout) step 2. The chart refuses a pool without a class; there is no fallback to `talos` at render time. The source of the default is either a platform value or a default-class annotation on one class; [Open questions](#open-questions) keeps the choice between the two. Out of the box the default is `talos`. Existing pools get the field from the migration in [Upgrade and rollback compatibility](#upgrade-and-rollback-compatibility). The built-in names still resolve without an object, whichever class is the default.

**ComputePlane pools.** A ComputePlane renders its pools' values itself, through an allowlist of pool fields (`pick` in `packages/extra/computeplane/templates/cluster.yaml`), and keeps its rule that a tenant cannot pick the worker OS (the comment above that allowlist): the allowlist does not pass `nodeGroupClassName` from the tenant. In this rollout the module writes the built-in `talos` into every node group on every render, and the migration writes the same value into existing ComputePlane pools. Existing ComputePlanes already run on the chart's Talos defaults, because the module drops the pool's Talos fields, so this changes nothing for them. Choosing another class for a ComputePlane is [open question 13](#open-questions).

### 3. Substrate and OS

The class is the OS boundary and the substrate is the infrastructure boundary. An OS has to provide, for each substrate it supports, an image in that substrate's format and a bootstrap template the substrate's machine template can boot:

| | KubeVirt | Proxmox |
| --- | --- | --- |
| Talos | raw disk from the Image Factory over HTTP, or a CDI clone of a golden; `TalosConfigTemplate` | clone of a Talos VM template selected by tags; `TalosConfigTemplate` |
| Kairos | container disk imported by CDI, EFI firmware; `KairosConfigTemplate` with `distribution: kubeadm` | not supported: needs a Proxmox VM template built from the Kairos disk |

Adding a substrate means filling its column for each family, and adding a family means filling its row; neither adds an OS-specific pool field. What counts as an entry depends on the family. A Talos class always has a KubeVirt entry: its `substrates.kubevirt`, or the Image Factory with the class's `talos.*` settings when that key is absent. It has a Proxmox entry only when `substrates.proxmox` is set. A Kairos class has only a KubeVirt entry, which is its `image`, or the platform disk when `image` is omitted. The chart refuses a pool whose class has no entry for the pool's substrate, with a message naming both.

### 4. Bootstrap

A pool on a Kairos class renders a `MachineDeployment`, a `KubevirtMachineTemplate` with EFI firmware (AuroraBoot builds the disk as an EFI disk, `disk.efi=true`), a `MachineHealthCheck` and a `WorkloadMonitor`, and its `kairos-reconcile` Job produces a `KairosConfigTemplate` with `distribution: kubeadm`.

The `KairosConfigTemplate` needs the tenant apiserver Service ClusterIP and the management CoreDNS ClusterIP, which exist only after the control plane is running. As in the Talos path, a reconcile Job waits for them and applies the template. Tenant values reach it only as data in a mounted ConfigMap, so no tenant value is script text. `envsubst` substitutes exactly four variables: `SVC_IP` and `COREDNS_IP`, which the Job reads from the two Services, and `RELEASE` and `NS`, the parent cluster's release name and the pool's namespace, which the chart passes to the Job as quoted environment values. The release name is `kubernetes-<cluster>`, built from the pool's `cluster` field, the name of the parent `Kubernetes` object, unless a ComputePlane sets `clusterReleaseName`; no other tenant value is substituted. The Job can get, patch and update only its own pool's template; `create` stays namespace-wide, because RBAC cannot narrow it by name.

The worker joins `https://<release>.<namespace>.svc:6443`. kubeadm also takes the server name from the `cluster-info` ConfigMap Kamaji publishes, so the name must resolve during the first join; the template writes it to `/etc/hosts` with the Service ClusterIP, the counterpart of Talos `extraHostEntries`. #4911 makes the tenant `KamajiControlPlane` publish the tenant CoreDNS address (`dnsServiceIPs`), so kubeadm-joined kubelets get `clusterDNS`.

Kairos applies its bootstrap data on the first boot and keeps that copy. Any change to the template therefore takes effect only on new machines, and the chart names the template by a hash of its chart inputs so that every change to them rolls the pool. The runtime addresses the Job fills in are left out of that hash, as in the Talos template. The provider attempts the join once per machine. A failed join leaves a Machine without a Node, which is the MachineHealthCheck's case.

### 5. The worker image

**Who builds it.** Cozystack builds the platform images in its own CI, from `packages/apps/kubernetes-nodes/images/kairos-worker`, one per Kubernetes minor listed in that chart's `files/versions.yaml`. The OS image of each minor is published next to its disk; as of 2026-10-27, #4911 publishes it as `kairos-worker-base-<minor>`. A hoster image is built by the hoster `FROM` that OS image, so kubelet, kubeadm, containerd and Hadron match the platform image of that minor, and turned into a disk with the same AuroraBoot recipe.

**Versioning.** The platform image of a minor carries the patch `files/versions.yaml` pins for it (v1.35.6 for v1.35 on main). The disk is tagged with the package version and pinned by digest in `images/kairos-worker-<minor>.tag`, and the published OS image of the same minor gets its own `.tag` file next to it, so a hoster can pin `FROM` by digest and the release tooling that enumerates `.tag` files (`hack/lib/image-refs.sh`) retags and mirrors it with the rest. #4911 rebuilds the disk of every minor on every release, and as of 2026-10-29 the build is not reproducible: two CI builds of unchanged inputs gave different digests. The digest is part of the disk URL in the pool's `KubevirtMachineTemplate`, so every Cozystack release rolls every pool on a Kairos class without `image`, the platform `kairos` class included. A build that gives the same digest for the same inputs, or rebuilds only the minors whose inputs changed, is a condition for leaving experimental (see [Rollout](#rollout)). After that, a Hadron, containerd or runc bump rebuilds every minor, and a Kubernetes patch bump rebuilds the minor it touches.

**Where it is stored.** The disks go to `ghcr.io/cozystack/cozystack/kairos-worker-v1.31` to `kairos-worker-v1.35`, and the OS images to `ghcr.io/cozystack/cozystack/kairos-worker-base-v1.31` to `kairos-worker-base-v1.35`. Each worker's DataVolume imports its disk from the registry without credentials, so the packages must be publicly pullable, like the other platform images. Git carries amd64 digests; a release adds arm64, as #4911 does today.

**How a hoster image reaches a worker.** Through `image.reference` only, imported per worker the same way as the platform disk, so the hoster's registry has to serve it without credentials. A disk that needs credentials, or one whose content must not reach every tenant, waits for the shared golden catalog listed in [Scope](#scope-and-related-proposals); this proposal does not add a second catalog for worker disks.

**The patch pin.** For a Kairos class without `image`, the platform `kairos` class included, the Machine version and the image both follow `files/versions.yaml`, and a Cozystack upgrade that moves the patch rolls those pools, as it does for Talos pools. Until a release with unchanged image inputs leaves the platform disk digests unchanged, every Cozystack upgrade rolls them as well, see Versioning above. For a class that names its own image the Machine version, the image and the `kubernetesVersion` field of the `KairosConfigTemplate` all come from the class. For kubeadm workers that field is informational, and the provider checks the image's kubeadm against the Machine's version, but it is part of the hash that names the template, so taking it from `files/versions.yaml` for a class that names its own image would roll its pools on every patch bump. The chart checks only that the class's minor equals the pool's `version` and that the pool is not ahead of its control plane. A Cozystack upgrade therefore does not break the render of a pool on a class that names its own image, and the hoster can publish the next class before or after the upgrade.

### 6. Upgrade

Workers are immutable. A new Kubernetes patch or minor, a new Hadron, or a new class that names its own image means a new disk and a new template, and the `MachineDeployment` rolls, as a Talos pool does when its image or machine config changes. Nothing on the node is upgraded in place. Until a release with unchanged image inputs leaves the platform disk digests unchanged, pools on a Kairos class without `image` also roll on every Cozystack release, see [The worker image](#5-the-worker-image).

Moving a pool on a class that names its own image to a new patch means pointing `nodeGroupClassName` at the class that carries it. Moving to a new minor means changing the pool's `version` and its class in the same edit, because the chart refuses a class whose minor differs from `version`, and the control plane has to be on that minor first. Switching between two classes of the same bootstrap family is allowed, and rolls the pool when the two classes render differently.

### 7. MachineHealthCheck and remediation

The pool's `MachineHealthCheck` is the same object for both OSes, with the same `nodeStartupTimeout` (default 20m) and `maxUnhealthy` (default 50%). Under the default, a pool of one machine is never remediated, because half of one rounds down to zero (the field description in `values.yaml` says so); this applies to Talos pools as well.

No test in cozystack/cozystack pins remediation on a Kairos pool. In my test environment, a single-machine Kairos pool whose machine never became a node was marked unhealthy with `NodeStartupTimeout` and not remediated, and the MachineHealthCheck status gave the reason as the one above: one machine, one unhealthy, `maxUnhealthy: 50%`. The test plan below uses a pool of at least two machines, or an explicit `maxUnhealthy`.

### 8. Autoscaling

The tenant cluster's autoscaler does not depend on the OS: it scales each pool's `MachineDeployment` within the limits in that pool's annotations. For scale from zero, cozystack/cozystack#4927 adds the pool's labels and taints to the capacity annotations already on the `MachineDeployment`, and #4949 adds the role labels and the GPU count. They are the same for both OSes because the VM shape comes from the `KubevirtMachineTemplate`. The autoscaler reads Cluster API through v1beta1 (`CAPI_VERSION=v1beta1`, set in #4902).

Scale from zero has not been tried on a Kairos pool. The `maxNodeProvisionTime` default (30m) and `nodeStartupTimeout` were sized for Talos boots; a Kairos first boot adds a reset into the installed system and a reboot. How much time that adds has not been measured.

### 9. Labels and taints

As in #103: `labels` and `taints` on the pool, rendered as kubeadm `nodeRegistration` on Kairos and as `machine.nodeLabels` and `registerWithTaints` on Talos, with labels in the Cluster API domains on the `MachineDeployment` template. Nothing Kairos-specific is added.

### 10. GPU guest on Kairos

This section is the Kairos part of GPU support: what a hoster's GPU image contains and how it is checked. The GPU class, the mode, the license and its delivery come from `gpudevice`; a GPU pool is a pool that names a class whose image carries the driver and has `gpus` entries. A hoster guide for building the images goes into the documentation.

**What was tested.** In my test environment, a Hadron guest with the 595 vGPU guest driver was licensed against an NVIDIA License System server with a compute (C-series) profile and `FeatureType=4`, and ran CUDA. The license was NVIDIA AI Enterprise: compute profiles are licensed through NVIDIA AI Enterprise, not through NVIDIA vGPU software. Three things were needed beyond installing the driver:

- `/var/lib/nvidia` must exist, created by a `tmpfiles.d` entry.
- `/dev/nvidia-uvm` must be created with `nvidia-modprobe -u -c 0` before `nvidia-persistenced` starts, because the modules load before udev processes its rules.
- The driver userspace is glibc-linked, so it lives in a glibc prefix.

The data center driver in a Hadron guest with a passthrough GPU has not been tested. It is also glibc-linked, so it needs the same prefix; whether it needs the other two fixes is not verified. CUDA Unified Memory (`cudaMallocManaged`) is disabled by default on vGPU, a documented NVIDIA limitation.

**The recipe.** A directory `packages/apps/kubernetes-nodes/images/kairos-gpu-worker` holds a Dockerfile, and the chart's Makefile gets a target `image-kairos-gpu-worker-<mode>-<minor>`, where the mode is `vgpu` or `passthrough`. The Dockerfile builds `FROM` the platform OS image of that minor and adds a layer with:

- the guest kernel modules and the driver userspace from a `.run` passed in through a named build context: the vGPU guest driver for `vgpu`, the data center driver for `passthrough`, with the userspace, `nvidia-persistenced` and `nvidia-smi` in a glibc prefix outside `/usr/local`;
- `nvidia-container-toolkit`, with `nvidia-ctk` in `/usr/bin`, linked at boot to the path the gpu-operator contract below requires;
- units that run `nvidia-modprobe -u -c 0` before `nvidia-persistenced`;
- for `vgpu` only, `nvidia-gridd`, the `tmpfiles.d` entry for `/var/lib/nvidia`, a unit that starts `nvidia-gridd` after `nvidia-persistenced`, and the unit that carries out the `gpudevice` license contract, described below;
- a containerd runtime for `nvidia`, with CDI enabled;
- two boot units: one that links `nvidia-ctk` into `/usr/local/bin`, and one that creates the `/dev/char` symlinks for the NVIDIA devices.

The target turns the result into a disk with AuroraBoot, as for the platform disk, and pushes it to a registry the hoster names. Cozystack's tree, CI and registries never contain NVIDIA driver binaries: CI never runs the target, and the default `make image` does not include it. A class can name such a disk only through `reference`, which has to be publicly pullable. A passthrough image can go that way if the hoster may publish it. A vGPU image carries the vGPU guest driver, which is licensed and may not be published, so Kairos vGPU workers wait for the shared golden catalog with private sources.

**License delivery.** `gpudevice` defines it in [its section 6](https://github.com/cozystack/community/pull/99), "vGPU entitlement and license delivery", and its decision 0018: its VMI webhook adds a disk with the volume label `GPULICENSE` to a VMI of a vGPU class whose `license` is set. The Kairos vGPU image includes a unit that carries out the guest contract of that section; the paths and the `nvidia-gridd` configuration are defined there.

**The `test` stage.** Every check of the platform `test` stage, plus checks that need no GPU: the modules match the kernel, the glibc prefix resolves every library of the driver tools, the units are ordered, containerd names the `nvidia` runtime, and the boot units for the `nvidia-ctk` link and the `/dev/char` symlinks and the loader configuration for the glibc prefix are in place. The check on real hardware is a documented manual step.

**The gpu-operator contract.** The gpu-operator addon is per tenant cluster, but the OS is per pool, so a cluster with a Talos pool and a Kairos pool runs one gpu-operator for both. A Kairos GPU image therefore has to meet the contract the addon's default already expects on Talos, with no override for Kairos: the driver libraries resolve from `/`, `nvidia-ctk` is at `/usr/local/bin/nvidia-ctk`, and the `/dev/char` symlinks for the NVIDIA devices exist, because the addon sets `DISABLE_DEV_CHAR_SYMLINK_CREATION=true` and leaves them to the host, which on Talos is the extension (`packages/apps/kubernetes/templates/helmreleases/gpu-operator.yaml`). The Kairos image creates them at boot. On Kairos the persistent partition is mounted on `/usr/local` during boot ([Kairos documentation](https://kairos.io/docs/architecture/immutable/)) and hides anything the image puts there, so the image keeps `nvidia-ctk` in `/usr/bin` and links it into `/usr/local/bin` at boot. Whether the gpu-operator validator and `nvidia-ctk cdi generate` find the driver libraries in the glibc prefix is not verified; if they do not, the image adds the prefix to their search paths. A build stage without a GPU cannot show it, so it is part of the manual check on hardware.

### 12. What a Kairos pool costs

- A second image pipeline in Cozystack CI: five minors, two architectures, a kubelet built from source, and a rebuild for every Hadron and Kubernetes patch. A static kubelet build in Hadron upstream would remove the source build; it is a possible step, not part of this rollout.
- A roll of every pool on a Kairos class without `image` on every Cozystack upgrade, with a disk import per worker, until a release with unchanged image inputs leaves the platform disk digests unchanged; see [The worker image](#5-the-worker-image).
- Hadron v0.5.3 ships kernel 7.2. In my test environment tenant Cilium 1.19.5 failed on that kernel, and the upstream issue reports the same on 1.19.4, 1.19.7, 1.20.0 and 1.20.1 ([cilium/cilium#48016](https://github.com/cilium/cilium/issues/48016), closed). Main ships 1.20.2, and a Hadron v0.5.3 worker ran with tenant Cilium 1.20.2 in the same environment. A Hadron bump therefore needs a check against the tenant CNI version.
- A young provider (v0.2.x) and a young distribution, with a release cadence Cozystack does not control.
- An SSH login with root through sudo: the worker has a `kairos` user in the `admin` group, with no password login and the pool's single `sshKeys` entry. Talos workers have no SSH and no shell.
- About 381 MB imported per worker for the v1.35 platform disk.

## User-facing changes

- Hoster: a new `NodeGroupClass` resource; the platform installs `talos` and `kairos`. Talos settings that tenants set on pools today (`talos.*`, `osImage`, `kernelModules`, `proxmox.templateTags`) become class content, so the choice of schematic, modules and image source moves from the tenant to the hoster. A tenant that needs other Talos settings gets them by the hoster publishing a class. Documentation for building a Kairos image `FROM` the platform image, building a GPU image ([section 10](#10-gpu-guest-on-kairos)), and publishing a class.
- Tenant: the `talos` block of the `Kubernetes` application is removed, with the pool fields. A `nodeGroupClassName` field on `KubernetesNodes`, defaulting to the cluster's default class, and `sshKeys`, the same field as on `vm-instance`, limited to one key on Kairos for now. The OS-specific fields are gone from the pool. The dashboard needs to list available classes; how a tenant reads cluster-scoped classes is an open question.
- Existing pools keep their render: the migration below moves their settings into classes without changing it. After step 3 the Cozystack API refuses a create or update of a pool that carries `talos.*`, `osImage`, `kernelModules` or `proxmox.templateTags`, or of a `Kubernetes` application that carries `talos`, with an error that names the field and says to move it into a class. Manifests kept outside the cluster with those fields, in GitOps or scripts, stop applying until they name a class instead. Dropping the fields with a warning would let an old manifest create a pool on the default class that boots a different OS without anyone noticing. A pool whose stored Talos values equal the defaults of both the old and the new release is moved to `talos` and follows later Talos default changes.

## Upgrade and rollback compatibility

**Moving Talos settings into classes.** A platform migration moves them. It has to run in every platform variant, before the new chart renders the pools; today the platform renders its migration hook only when `migrations.enabled` is set (`packages/core/platform/templates/migration-hook.yaml`), and only the `values-isp-*` variants set it. The migration removes the old fields from each pool it moves. As a safety net, the chart refuses to render a pool that still carries any of the old Talos fields, whether or not it names a class, rather than ignoring them. For each existing pool it reads the pool's Talos settings (`talos.*`, `osImage`, `kernelModules`, `proxmox.templateTags`). A pool with no stored Talos values, or with stored values equal to the chart defaults of both the release it is upgraded from and the release it is upgraded to, is pointed at the built-in `talos` class. The migration carries the Talos defaults of every release it can upgrade from, so an upgrade that skips releases compares against the release actually installed. For every other distinct set of settings in a namespace the migration creates one Talos class, named deterministically by a hash of the namespace and the set, so pools of one tenant with the same settings share one class, and points each such pool at it. A generated class takes the pool's `osImage` as its `substrates.kubevirt.osImage` as it is, an empty `osImage: {}` included, and its `proxmox.templateTags` as `substrates.proxmox.templateTags`. A generated class carries the UID of the namespace its pools came from, in a label, and the chart compares it with the UID of the release namespace, read through a `lookup` of the Namespace, and refuses a pool in any other namespace that names it. The migration also writes `nodeGroupClassName` into every pool. For ComputePlane pools it writes `talos`, the same value the module writes on its next render, so no pool waits for that render. The parent `Kubernetes` application loses its `talos` block too (`talos.version`, `schematicID` and the other keys in `packages/apps/kubernetes/values.yaml`), removed by the same migration. Its only reader at render time is the Talos to Kubernetes support-matrix check in `packages/apps/kubernetes/templates/cluster.yaml`; ComputePlane drops the key and `kubernetes-nodes` reads only its own. An earlier platform migration copied the parent's `talos` block into every pool it split out (`pick(.; ["version","talos"])` in migration 56), so many pools store a full `talos` block and get a generated class if the defaults have moved since. The check moves to the pool's render, which already has it for the pool's own `talos.version`: the Talos version of the class against the pool's `version`, and the pool's `version` is already held at or below the control plane's. The pool field description "Keep in sync with the parent cluster's `talos`" goes with it. After the move a pool on `talos` follows the platform's Talos defaults from then on, while today a pool that stores those values keeps them until it is edited; a pool on a generated class keeps its values. The required property is that the move itself rolls no pool: every pool renders byte for byte as the same release renders it from the old pool fields. The helm unit tests pin that against golden snapshots.

**Kairos pools.** A pool on the `kairos` class or a hoster's Kairos class is new; nothing existing changes when Kairos support is added.

To move a Talos pool to Kairos, create a second pool on a Kairos class, move workloads by cordoning and draining the Talos nodes, scale the Talos pool to zero and delete it. Changing `nodeGroupClassName` between a Talos class and a Kairos class on a running pool is refused in the first release, in either direction, by a guard that compares the bootstrap template kind of the live `MachineDeployment` with the one the class's bootstrap family asks for. A Cluster API rolling update between bootstrap providers is what `kubernetes-nodes-split` Phase 1 used to move from kubeadm to Talos, so allowing the switch in place is possible later; see [Open questions](#open-questions).

Rolling back a moved pool means scaling the Talos pool back up and deleting the Kairos pool. Steps 2 and 3 ship in one release, so reverting to the release before it undoes both. The Kairos pools have to be gone first: the old chart ignores `nodeGroupClassName`, renders such a pool as Talos and has no guard against the switch, so it would roll the Kairos workers onto Talos. The provider and the class objects do not need removing first. Pools on Talos classes other than the built-in `talos` have no automatic way back, because platform migrations only run forward (`packages/core/platform/images/migrations/run-migrations.sh`). Before the revert the hoster runs a restore script that step 3 ships: it copies the Talos fields from each Talos class other than the built-in `talos`, generated or created by the hoster after the move, back into the values of every pool on it, writing the HelmReleases directly, since the Cozystack API refuses those fields after step 3. The script does not restore the parent `Kubernetes` application's `talos` block; its only reader is the support-matrix check, so this is harmless as long as the default Talos of the release reverted to supports the parent's version. The script is a runbook tool, not a reverse platform migration. Without it such a pool renders with the old chart's defaults after the revert and rolls, and a Proxmox pool without `templateTags` fails to render. Between the restore and the revert the running chart refuses those pools, because they carry the old fields again; their HelmReleases retry and fail, and no object changes until the old chart takes over. A pool moved to the built-in `talos` needs nothing restored: it stored no Talos values, or values equal to the defaults of the release being reverted to, which the old chart renders anyway.

## Security

- Classes are hoster input. A class decides what OS image and Talos configuration every worker of a pool boots, so only the hoster creates them; tenant roles come from RoleBindings and do not reach cluster-scoped kinds. Generated classes are the exception in content: they carry what a tenant once set on its pools, including `imageFactoryURL`, `installerRepository`, `registryMirrors` and `imageFactoryCA`. Only pools in the namespace a generated class came from can use it. The class records the namespace's UID rather than its name, because a namespace deleted and created again under the same name belongs to a new tenant and must not inherit the old tenant's mirrors or CA. If tenants get read access to all classes (open question 3), every tenant sees that content.
- A Kairos class names its image by digest, so the bytes a pool boots cannot change under it. A Talos class pins its image by schematic and version, through the Image Factory or a Proxmox template, not by bytes.
- No Talos secrets on Kairos pools: no Talos token, no machine CA. The provider mints the join token and stops before minting a token when the CA in the `<cluster>-kubeconfig` Secret does not match the `<cluster>-ca` Secret.
- Tenant input to the bootstrap template is YAML-quoted data in a ConfigMap, never script text. The reconcile Job can patch only its own pool's template.
- SSH. Password login is disabled (`userPassword: "*"`). With empty `sshKeys` there is no login at all. The key reaches the node as data in the provider's bootstrap config, never as script text, like the rest of the tenant input. A key is a break-glass path for the tenant, not a management channel. The `kairos` user is in the `admin` group and has sudo, as Kairos gives its default user ([Kairos configuration reference](https://kairos.io/docs/reference/configuration/)), so the key gives root on the worker; that is deliberate, and access is by key only.
- Images that may not be published. `reference` has to be publicly pullable, so an image that may not be published, such as one carrying the NVIDIA vGPU guest driver, is not delivered through `reference`. It waits for the shared golden catalog with private sources.

## Failure and edge cases

- Pool names a class that does not exist → the render fails with the class name; no objects change.
- Pool without `nodeGroupClassName` → the render fails and says the field is required.
- A pool names a generated class from another namespace, or from an earlier namespace of the same name → the render fails and names the class.
- A hoster class deleted while in use → existing Machines keep running and scale-ups use the current templates; the next render fails until the class is back.
- A class without an entry for the pool's substrate, such as a Kairos class on a Proxmox pool or the built-in `talos` class on a Proxmox pool → the render fails and names the class and the substrate.
- Platform image missing for the pool's minor → the render fails and names the minor.
- Image kubeadm version differs from the Machine's → the join script on the node refuses the join; the Machine never gets a Node; MachineHealthCheck applies.
- Registry refuses the pull → the DataVolume stays in import, the Machine stays in Provisioning, and the error is on the DataVolume. MachineHealthCheck replaces the Machine after `nodeStartupTimeout`, within `maxUnhealthy`, and the replacement fails the same way while the registry keeps refusing.
- Cozystack upgrade → pools on a Kairos class without `image` roll, see [The worker image](#5-the-worker-image); pools on a class that names its own image are not rolled by the platform disk or the pinned patch; a release that changes the chart's Kairos templates rolls them, as it rolls Talos pools.
- A class with a tag-only `reference` → refused by kube-apiserver at create, through the CRD's CEL rule.
- Tenant apiserver Service is re-addressed → the pool does not roll, because the ClusterIP is kept out of the template's hash. The template is refreshed only when the reconcile Job runs again; see [Open questions](#open-questions).
- Join fails on first boot → no retry on the node; MachineHealthCheck replaces the machine after `nodeStartupTimeout`, within `maxUnhealthy`.
- A Talos pool switched to a Kairos class, or a Kairos pool to a Talos class → the render fails and says to create a new pool.
- `gpus` on a Kairos pool whose image has no driver → the VM gets the device and the guest cannot use it; the chart does not check the image. A vGPU class on a Talos pool is refused by `gpudevice` admission instead.
- A migrated pool whose generated class is deleted → as for any deleted class in use.

## Testing

- Unit (helm unittest). Every existing pool render unchanged after the migration, for pools on default settings and on non-default ones, on both substrates; Kairos render for classes with and without `image`; Machine version and the template's `kubernetesVersion` taken from the class; a patch bump in `files/versions.yaml` leaving every object of a pool on a class that names its own image unchanged, the `KairosConfigTemplate` name included; class minor checks; guards for a missing class, a missing image, a missing substrate entry and a bootstrap-family switch in both directions; `gpus` entries passed through unchanged on both families.
- Migration. It runs in every platform variant before the chart renders pools, and every pool gets `nodeGroupClassName`. Pools with no stored Talos values or with values equal to the defaults of both releases get `talos`. Pools of one namespace with equal Talos settings get one generated class labelled with that namespace's UID, and a pool storing values that equal the defaults of only one of the two releases gets a generated class too. An unset `kernelModules` and an explicit `[]` stay distinct in the class. A second run changes nothing. Every ComputePlane pool gets `talos`.
- Migration guards. The Cozystack API refuses a create or update with any old Talos field on a pool or `talos` on a `Kubernetes` application, naming the field. A pool with any old Talos field is refused by the chart, with or without a class, and so are a pool without `nodeGroupClassName` and a pool naming a generated class from another namespace, including a class whose namespace UID differs from that of a namespace with the same name. The migration leaves no old field on a pool it moved.
- Restore script. On a copy of migrated pools the script puts the Talos fields back, after which the chart of the release before step 2 renders each pool byte for byte as before the migration; a pool created after the move on a hoster's Talos class gets that class's fields as pool values.
- Class admission. kube-apiserver refuses, through the CRD's CEL rules, a change to a class's `spec`, a tag-only `reference`, fields of the other bootstrap family, and a `talos` or `kairos` object whose `spec` differs from the built-in one, while a default-class annotation on it is accepted.
- Default class. A pool created through the API without the field gets the cluster's default; changing the default later leaves existing pools unchanged; an update without the field keeps the stored class. A ComputePlane re-render writes `talos` into every node group and ignores a tenant-supplied `nodeGroupClassName`.
- Parent `talos`. After the migration the `Kubernetes` application has no `talos` block, and a pool whose class has a Talos version that does not support the pool's `version` fails the render.
- SSH keys. A Kairos pool with two keys in `sshKeys` fails the render; with one key the key reaches `sshPublicKey`.
- GPU kernel modules. A Talos pool with a class entry for an `nvidia.com/*` GPU class gets the same modules as one with the matching `name` entry.
- Image. The `test` build stage of every minor: static kubelet and kubeadm, exact versions, units enabled, kubelet unit flags present. For GPU images, the `test` stage of [section 10](#10-gpu-guest-on-kairos), run by the hoster at build time.
- Build gating (bats). Every Kubernetes minor of the pool chart has a disk `.tag` pinned by digest and an OS image `.tag` next to it, no `.tag` is left for a minor the chart no longer offers, and the release tooling enumerates the OS images.
- End to end, join. In the `kubernetes-latest` suite: create a pool on the `kairos` class, wait for the Node to become Ready, check `providerID` and the cluster-namespace annotation, run a pod on it. #4911 already carries this step with a 35-minute ceiling, which budgets the job at 250 of its 255-minute cap.
- End to end, remediation and scale from zero. Two new jobs, since `kubernetes-latest` has no room left and one job for both would not fit. As the Kairos step in #4911 counts, each new pool waits for its HelmRelease (1 + 2 minutes) and its MachineDeployment (1 + 2), 6 minutes, and each join for a Running Machine (1 + 15) and a Ready Node (3), 19 minutes; machines of one pool join in parallel. The figures below mix one measurement with ceilings: the install of about 28 minutes is measured (27m52s on CI run 39163455078, quoted in the `kubernetes-latest` suite in #4911), while the 67-minute cluster bring-up and the 22-minute teardown are the ceilings that suite sets, not measurements. Each job also runs steps outside the suite, which add 40 minutes: Prepare environment, 2 minutes (2m05s measured on the same run, the step has no ceiling), Collect report, 30 minutes (its `timeout-minutes` in the workflow; 28s on that run), and Tear down sandbox, 8 minutes (8m20s measured, no ceiling). The 255-minute job cap is the one #4911 sets; main caps the E2E job at 215 minutes, so these jobs need #4911's cap or their own.
  - Remediation job. A Kairos pool of two machines; stop one worker VM and expect a replacement Node; then, with an explicit `maxUnhealthy: 100%` for this step, a pool whose class points at a disk that cannot be imported, whose Machines are replaced after `nodeStartupTimeout`; the import breaks through the class, so every Machine of the pool fails, and the default `maxUnhealthy` would stop remediation (section 7). Test budget: the two-machine pool, 6 + 19 = 25; the stopped worker, `readyUnknownTimeout` (5m) plus the node lifecycle controller's grace period (about 1m) and a replacement join (19), 25; the broken-disk pool, 6 + `nodeStartupTimeout` (20m) = 26; and 10 minutes of reads; 25 + 25 + 26 + 10 = 86 minutes. Job: 28 + 67 + 86 + 22 + 40 = 243 minutes, under the 255-minute cap.
  - Scale-from-zero job. 0 to 1 and back to 0 through the autoscaler. Test budget: the pool at zero, 6; the scale-up within `maxNodeProvisionTime` (30m), which covers the join, plus a Ready Node (3), 33; the autoscaler's scale-down delay after a scale-up (10m by default; the chart sets only `--scale-down-unneeded-time=30s`); and 10 minutes of reads; 6 + 33 + 10 + 10 = 59 minutes. Job: 28 + 67 + 59 + 22 + 40 = 216 minutes, under the cap.
- End to end, upgrade. A new job, because no Chainsaw suite performs an upgrade today: install the last release without Kairos support, create Talos pools with default and with custom Talos settings, upgrade to the candidate, and check that the migration ran, that every pool names a class and carries no old Talos field, and that the chart refuses no pool. Whether the move itself rolls a pool is not checked here, because the candidate may change Talos defaults or pool templates on its own; the golden-snapshot unit tests prove it, comparing the candidate's render from the old pool fields with its render after the migration. Budget: one install of about 28 minutes (measured, as above) and one upgrade to the candidate, estimated at the same 28 minutes since no upgrade has been measured, one cluster bring-up under its 67-minute ceiling, two Talos pools at 6 + 19 = 25 minutes each, 10 minutes of checks and the 22-minute teardown ceiling: plus the 40 minutes of steps outside the suite: 56 + 67 + 50 + 10 + 22 + 40 = 245 minutes, under the 255-minute cap. Once a release with unchanged image inputs leaves the platform disk digests unchanged, the same job upgrades between two releases with the same image inputs and the same render of the Kairos templates, and checks that no Machine on the `kairos` class is recreated.
- GPU, manual on hardware. In this rollout, passthrough only: the pool joins, `nvidia-smi` sees the whole GPU, and a CUDA pod scheduled through the gpu-operator addon passes with no license. After the shared catalog, vGPU: the pool joins on first boot, `nvidia-smi -q` shows `Licensed`, and the same CUDA pod passes. Cozystack CI cannot run this.

## Rollout

1. Cluster API v1.13.7 (cozystack/cozystack#4902).
2. `NodeGroupClass` with the `talos` and `kairos` classes and Kairos pools (#4911), the provider built from v0.2.1 with no patches to its code, and the platform disks and OS images published publicly. Before it merges, #4911 changes to match this design: the class names a bootstrap family in `bootstrap` instead of `os`; `reference` must carry a digest; `kairos.sshPublicKey` is replaced by `sshKeys`; `gpus` passes through on Kairos pools instead of being refused; the default class is written into the pool at creation by the Cozystack API instead of being computed in the chart, the ComputePlane module writes `talos` into every node group, and every default of the field is removed: the `+kubebuilder:default` in the API type and the `nodeGroupClassName="talos"` `@param` line of the chart's `values.yaml`, from which the values, `values.schema.json` and the cozyrd defaults are generated, since `applySpecDefaults` would show a schema default on read and a read-modify-write client would store it; the pool has no kubectl image override, and the `kairos-reconcile` Job takes its image the same way as `talos-reconcile` does on main since the override was dropped there. None of these has shipped in a release, so none needs a migration. Open question 4, the source of the cluster's default class, is settled before step 2 merges, because the API writes that default. Kairos is marked experimental in the docs and the dashboard.

Steps 2 and 3 merge back to back with no release cut between them, and ship in the same release, because step 2 stops the chart from computing a default and only the migration of step 3 writes the class into existing pools.

5. The Kairos GPU image recipe, its `test` stage and the hoster guide, after item 2 of the `gpudevice` rollout. Kairos vGPU workers also wait for the shared golden catalog with private sources, a future proposal.

## Open questions

1. Single-machine pools and `maxUnhealthy`. The default `50%` never remediates a pool of one, on Talos and Kairos alike. Should the chart pick a threshold that remediates small pools, or keep the default and document it?
2. Class deletion. Should deleting a class that pools reference be refused, and by what (a finalizer set by a controller, or an admission policy)?
3. Tenant view of classes. Tenants need to see which classes exist to choose one. Read access to a cluster-scoped kind through a tenant RoleBinding does not work, so this needs either a ClusterRole for listing or an aggregated list exposed through the Cozystack API. The closest precedent is `SchedulingClass`, the hoster's class in the same group: its `cozy:schedulingclass:view` role is aggregated into the tenant view role, which tenants receive through a RoleBinding, so that grant has no effect on the cluster-scoped kind, and `SchedulingClass` has the same open problem. Who may see the content of generated classes is part of this question. A working precedent for the first: `packages/system/dashboard/templates/rbac.yaml` binds read access to `storageclasses` and `backupclasses` to every authenticated user, the same shape a class list needs.
4. The default class. A platform value, or a default-class annotation on one class as for `StorageClass`?
5. In-place OS switch. Allow changing a pool between a Talos class and a Kairos class as a rolling update, or keep requiring a new pool?
6. Hadron cadence. Who watches Hadron and kernel CVEs, and how fast does a Hadron bump have to land in a Cozystack release?
7. Re-addressed apiserver Service. The reconcile Job writes the current ClusterIP into the template whenever it runs: on Talos it replaces the `TalosConfigTemplate` when CABPT's webhook refuses the changed spec (`packages/apps/kubernetes-nodes/templates/talos-reconcile-job.yaml`), and on Kairos it patches the template with a server-side apply, since the provider has no webhook for `KairosConfigTemplate` (`config/webhook/manifests.yaml` in v0.2.1). A re-address alone does not run the Job, though: its name is a hash of its own spec, and after `ttlSecondsAfterFinished: 600` it is recreated only by the next Helm upgrade of the pool, since drift detection is off for the pool's HelmRelease. Should a re-address trigger the Job, for both OSes?
8. A join contract and a custom class. Publishing what a worker needs to join (endpoint, CA, token source, Service and DNS addresses) in one object per tenant cluster, and a custom class whose bootstrap template the hoster supplies, would let a new OS family be added without a chart change. Both are deferred to their own proposal; which object carries the contract is open.
9. Data center driver on Hadron. The passthrough GPU image is untested. Does the data center driver need the same fixes as the vGPU guest driver?
10. Unlicensed state. Should a GPU node whose license client failed be tainted or reported?
11. gpu-operator and the glibc prefix. Do the validator and `nvidia-ctk cdi generate` find the driver libraries in the prefix, or does the image have to add it to their search paths ([section 10](#10-gpu-guest-on-kairos))?
12. Generated classes after a tenant is deleted. They are cluster-scoped and have no owner, so they outlive the tenant whose pools they came from, carrying the UID of a namespace that no longer exists. Should that UID drive their removal, and by what?
13. A class for a ComputePlane other than `talos`. A ComputePlane's pools take their Kubernetes version from the `kubernetes-nodes` chart default, since the module passes none, so only a class without a fixed version could serve them, and the tenant must still not pick it. Three simple ways do not work: a pin in an internal `_` key of the ComputePlane's values is removed by any update through the Cozystack API, which rebuilds the values from the application and filters `_` keys on read; a pin written when the API creates the ComputePlane never happens, because the tenant chart renders the ComputePlane's HelmRelease and the API does not create it; and a shared platform value read at render time moves every ComputePlane in the cluster at once when it changes. Where the choice lives, and who may change it, is open.

## Alternatives considered

**A Talos system extension per module.** The hoster builds an extension for each module and runs an image factory or its own image build for each Talos release. It keeps one worker OS, but every hoster carries a Talos build pipeline instead of one `FROM` layer, and the work repeats on every Talos release. For modules Sidero Labs already publishes, Talos with a schematic stays the better choice, and nothing here changes that.

**A general-purpose distribution image (Ubuntu) with kubeadm.** This is the path `kubernetes-nodes-split` removed. It brings a mutable OS and package management to every worker. Kairos keeps the image immutable and the update model "replace the machine", which matches how the pool already works. As a bootstrap family it remains possible later: a new family is a new value of `bootstrap` ([section 1](#1-nodegroupclass)), and a join contract that would make it cheaper is open question 8.

**A Kairos flavor based on Ubuntu instead of Hadron.** It would accept the glibc kubelet and glibc driver userspace as is. I keep Hadron anyway. Kairos is a CNCF project, and Cozystack can change Hadron upstream. My changes there were accepted, among them [kairos-io/hadron#741](https://github.com/kairos-io/hadron/pull/741) (FAT filesystems formatted with dosfstools instead of busybox), [kairos-io/hadron-layers#82](https://github.com/kairos-io/hadron-layers/pull/82) (an OpenZFS layer), [kairos-io/kairos#5523](https://github.com/kairos-io/kairos/pull/5523) (the install fails on an ESP that UEFI cannot mount) and [kairos-io/kairos#5522](https://github.com/kairos-io/kairos/pull/5522) (kernel command line tokens no longer evaluated as jq), plus the provider changes #148 and #149 from [section 11](#11-upstream-dependencies-and-what-cozystack-carries). Cozystack has no such path into Ubuntu. Whatever needs glibc, such as the NVIDIA userspace, goes into the image as a layer with its own glibc prefix, and that was tested with the vGPU guest driver ([section 10](#10-gpu-guest-on-kairos)). The cost stays: the kubelet is built from source for every minor and architecture, as [section 12](#12-what-a-kairos-pool-costs) lists. A hoster can still build a class from another flavor, provided it ships kubelet and kubeadm at the class's version.

**Drivers as containers in the tenant cluster.** Every tenant cluster, where the tenant is cluster-admin, would pull the hoster's driver image and would need the hoster's registry credentials. With a node image only the management cluster pulls it.

**OS and image fields on the pool (as in the first drafts of #4911).** Each pool would carry the image reference and each OS its own fields, and the chart would refuse or ignore every other OS's fields. An edit of a shared default would roll the pools of every tenant at once. The class keeps OS settings in one immutable object.

**Talos settings left on the pool, Kairos settings in the class.** The pool's API would stay Talos-shaped, and every later OS would either follow Kairos into the class or add pool fields. Moving the Talos fields is easier before Kairos pools exist than after.

**A second catalog for worker disks with credentials.** It would duplicate the VM golden catalog in the same namespace, with a second pull-Secret convention and a second answer to who may clone a golden. Private worker disks wait for the shared catalog instead.

**Ship #4911 as is and migrate to the class later.** It would need a migration for an API that no release had time to use. #4911 is not merged, so reworking it is cheaper.
