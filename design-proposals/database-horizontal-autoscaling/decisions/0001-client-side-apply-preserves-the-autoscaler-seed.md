# 0001. The autoscaler seed survives because the tenant HelmRelease applies client-side

- **Number:** `0001`
- **Date:** `2026-09-02`
- **Status:** Proposed (flips to Accepted on merge of the proposal PR)
- **Deciders:** `@scooby87, @lllamnyp`
- **Proposal:** [`../README.md`](../README.md)
- **Decided in:** [`cozystack/community#66`](https://github.com/cozystack/community/pull/66)
- **Implemented in:** [`cozystack/cozystack#3954`](https://github.com/cozystack/cozystack/pull/3954)

## Context

The proposal's §3 committed to *omitting* `.spec.instances` from the rendered engine CR under active autoscaling. With the field absent from the manifest, Flux would neither set nor revert it, and the HPA — writing the CNPG `Cluster`'s `/scale` subresource — would be its sole writer. That was the whole ownership argument, and on paper it deleted the contested-field problem outright.

Building it against the current platform disproved that a chart-only omit is safe. Two facts were in play. First, the platform's helm-controller was on `v1.5.0` (`internal/fluxinstall/manifests/fluxcd.yaml`), which defaults new HelmReleases to server-side apply and hardcodes `ForceConflicts = ServerSideApply` (`internal/action/install.go:53`, same in `upgrade.go`/`rollback.go`), so any field the chart *renders* is force-owned by Flux and reverted from the HPA's live value on every apply — and Flux performs an apply on every chart or values change, which every platform release triggers. Second, the omit handoff assumed the HPA already owned `.spec.instances` at the moment the field left the manifest; but an HPA claims the `/scale` field manager only when it actually writes (`rescale = desired != current`), so a cluster idle at its floor never writes, never owns the field, and the phase-2 omit prunes it — whereupon CNPG's CRD default (`instances: 1`) takes over and the quorum webhook rejects the cluster or standbys and their PVCs are shed. Closing that gap chart-only would need the runtime actor the design had deliberately removed.

A constant-seed alternative was therefore explored, and a reviewer ([@IvanHunters](https://github.com/cozystack/community/pull/66)) raised the objection that reopened the question: forcing client-side apply does not make a rendered constant a no-op, because Helm's three-way JSON merge computes its add-and-change delta from the *live* object, so an unchanged constant would still be re-asserted against a drifted live count. That objection is the reason this record exists.

## Decision

Under active autoscaling the chart renders `.spec.instances` as a constant seed `max(replicas, effectiveMin)` (never omitted), and the tenant HelmRelease applies **client-side**, forced per application by `release.cozystack.io/helm-server-side-apply: "false"` on the `ApplicationDefinition`. Under client-side apply helm-controller patches the CNPG `Cluster` — an unstructured/CRD object — from the previous-versus-new rendered manifest and, on the upgrade action every steady-state reconcile takes, does not consult live state (the two-way merge for unstructured objects), so the unchanged constant produces no patch and the value KEDA writes through `/scale` survives every reconcile. The one exception is the install-with-adoption recovery path, where the same forced client-side setting instead selects a three-way merge that *does* read live and rebases the seed; it is bounded and documented as a residual write path in Consequences below, not a steady-state behaviour.

## Why not the alternatives

- **Chart-only omit under active autoscaling (the proposal's own §3).** Lost on a structural fact, not a packaging detail: on helm-controller v1.5.0 a rendered field is force-owned under SSA and reverted, and the phase-2 omit prunes `.spec.instances` for any cluster idle at its floor (the HPA has not written `/scale`, so owns nothing), collapsing it to the CNPG default of 1. Both failure modes are unavoidable without a runtime writer the design removed. Verified live on dev9.
- **Constant seed under the platform-default server-side apply.** Same force-revert: SSA with `ForceConflicts` steals the rendered field back from `/scale` on every apply. Reproduced directly — a CRD grown out of band to 4 and re-applied via `helm upgrade --server-side --force-conflicts` with the chart rendering the lower constant reverted to the constant in one step.
- **Constant seed under client-side, accepting the reviewer's "three-way re-asserts from live" reading.** Refuted at the source. Helm v4's `createPatch` (`helm.sh/helm/v4 pkg/kube/client.go`) routes unstructured/CRD objects to a **two-way** `jsonpatch.CreateMergePatch(original, modified)` — the previous rendered manifest against the new one, live never read — and only takes the three-way `CreateThreeWayJSONMergePatch(original, modified, current)` path the objection quotes when `threeWayMergeForUnstructured` is set. helm-controller v1.5.0 never sets it (no reference anywhere in the controller), so the default two-way path applies. Confirmed empirically on Helm 4.0.4; helm-controller v1.5.0 embeds v4.1.1 (`go.mod`), whose `createPatch` routes unstructured/CRD objects through the identical two-way arm, so the result carries over: a custom resource drifted to 4 out of band, then `helm upgrade --server-side=false` with the chart rendering the constant 2 *and* changing an unrelated field — the field change applied, `spec.instances` stayed 4. Only `--server-side --force-conflicts` reverted it.
- **Pinning `.spec.instances` via the scale subresource across the apply (the proposal's named fallback).** Rejected: it re-introduces a runtime writer of the CR's spec, which is exactly the property §3 set out to eliminate. Client-side apply achieves the same guarantee with no actor.

## Consequences

- A new platform knob: a per-`ApplicationDefinition` annotation (`release.cozystack.io/helm-server-side-apply`) threaded into `Install`/`Upgrade.ServerSideApply` on the emitted HelmRelease (`pkg/config`, `pkg/cmd/server/start.go`, `pkg/registry/apps/application/rest.go`). It is general, not postgres-specific.
- The annotation is **per-kind**, so client-side apply reaches *every* Postgres, not only autoscaled ones. That trades away, for Postgres specifically, the SSA benefit v1.5.0 introduced — misplaced chart fields becoming hard errors rather than silently dropped (`docs/changelogs/v1.5.0.md`). Accepted because Postgres shipped on client-side apply before v1.5.0 without issue; a per-instance apply strategy that keeps SSA on for non-autoscaled databases is a possible follow-up. This basis is Postgres-specific: the next engine on the ladder (MariaDB, §Scope) does not inherit it and must re-establish and re-justify the client-side-apply trade — or adopt the per-instance strategy — when its autoscaling lands.
- One residual write path remains under client-side too: because the two-way patch propagates any change between the previous and new *manifest*, anything that moves the rendered `.spec.instances` rebases it in that single reconcile. Three triggers. Two stay inside the seed branch and so never drop below the quorum floor and never collapse to 1: a tenant edit to the seed's inputs (`replicas`, `autoscaling.minReplicas`, `quorum.maxSyncReplicas`), and — less obvious — a platform upgrade that changes how the seed itself is rendered (the `effectiveMin`/seed helper or a schema default), which rebases an HPA-grown count on the next apply even with no tenant edit. The third leaves the seed branch: flipping an already-grown cluster into a staging mode (`transition` or `dryRun`) while `enabled` stays true renders the *static* `instances: {{ .Values.replicas }}`, which is **not** clamped to the floor (only CNPG's own quorum webhook backstops it), so an unstaged flip sheds the live count all the way down to `replicas`. The first two are documented as the floor-change caveat in the chart's `values.yaml` (with a suspend-and-pin recipe for a deliberate rebase) and in §Upgrade (stage `.Values.replicas` to the live count, or use the `transition` flow); the platform-upgrade trigger is called out there too so an autoscaling-active chart bump is staged, not applied blind; the staging-mode flip is likewise staged in §Upgrade by pinning `.Values.replicas` to the live count before the flip.
- A second, much narrower residual path sits outside the two-way merge entirely: install-with-adoption. If a `Cluster` survives but its HelmRelease release-storage is lost (etcd recovery, namespace-secret cleanup, a Flux storage migration — and the postgres templates carry no `helm.sh/resource-policy: keep`, so an uninstall/reinstall remediation is excluded, it would take the `Cluster` with it), the next reconcile runs a Helm `install` against the existing object rather than an `upgrade`. On the install action `updateThreeWayMergeForUnstructured := TakeOwnership && !ServerSideApply` (`helm.sh/helm/v4@v4.1.1 pkg/action/install.go:503`) is **true today** — `TakeOwnership` defaults true and this design forces `ServerSideApply=false` — so Helm computes a three-way patch that reads live and rebases an HPA-grown `.spec.instances` back to the rendered seed in that one reinstall. It is bounded exactly as the seed-branch rebase is (the seed is `max(replicas, effectiveMin)`, so never below the quorum floor and never a collapse to 1), but it is a real shrink of the grown replica set during a recovery. Unlike the upgrade path it is not gated by any future upstream flag flip — it is live today by design, which is why the invariant above is stated for the upgrade/steady-state path specifically. It has no in-band staging recipe (it fires on a recovery reinstall, not a tenant edit); the mitigation is to expect it and re-stage `.Values.replicas` to the intended live count once the release storage is restored.
- A third residual path sits outside any patch — two-way or three-way — because it re-creates the object from scratch: backup/restore. An in-place restore, or a restore into an existing autoscaling-active application, runs through `internal/backupcontroller/cnpgstrategy_controller.go`, whose `purgeExistingCluster` **deletes** the CNPG `Cluster` and its PVCs outright (`client.Delete`, not a patch) before the resumed HelmRelease re-creates the `Cluster` via `bootstrap.recovery`. With the live object physically gone, Helm's apply takes the `Create` arm (`helper.Get` → `NotFound`), so the fresh `Cluster` is rendered straight from the chart at the seed `max(replicas, effectiveMin)` — the quorum floor, not the count the HPA had grown to. The restore controller is autoscaling-unaware (it patches only `Bootstrap`/`Backup` fields and never reads `replicas`/`autoscaling`), and this landed in main via [cozystack/cozystack#3959](https://github.com/cozystack/cozystack/pull/3959). It is bounded exactly as the others (never below the floor, never a collapse to 1) and the `ScaledObject`/HPA survive the purge, so the autoscaler re-grows the count to load once the restored cluster catches up. Unlike the seed-branch triggers, the staging recipe is **inapplicable by construction**: the purge exists precisely to erase live state, so pre-staging `.Values.replicas` to the live count cannot preserve it. This is a conscious rebase-to-seed on restore, not a data-loss path.
- Behaviour no longer splits by install date. Because the annotation forces `Install.ServerSideApply=false` and `Upgrade.ServerSideApply=disabled` uniformly, both pre- and post-v1.5.0 Postgres releases apply client-side; there is no population that silently stayed on SSA.

## Revisit if

the embedded Helm SDK's *upgrade* action starts passing `ClientUpdateOptionThreeWayMergeForUnstructured` — this is the real lever, not any helm-controller setting (helm-controller exposes none, as established above). Verified against `helm.sh/helm/v4` v4.1.1: `pkg/action/upgrade.go` does *not* pass the option, so it falls to its Go zero value (off) and the upgrade patch stays two-way for unstructured/CRD objects, which is what makes the steady-state no-op hold; the sibling `pkg/action/install.go:503` *does* compute it (`i.TakeOwnership && !i.ServerSideApply`), so the two actions are asymmetric today. If a future SDK made `upgrade.go` consistent with `install.go` by having it gain or pass `ClientUpdateOptionThreeWayMergeForUnstructured`, the upgrade-path patch would read live state and re-assert the constant, breaking the no-op on steady-state reconciles for *every* client-side release — the exact failure the reviewer described — and it would arrive through an ordinary Flux/helm-controller image bump that a maintainer watching "helm-controller settings" would not see, so with no repeatable test holding this behaviour this trigger is the only protection and must be diffed against v4.1.1 on the next SDK bump (the install-with-adoption three-way read is a separate matter: it is not the upgrade-path asymmetry above, it is already live today by design through `install.go`, and it is handled as the bounded recovery caveat in Consequences, not as a revisit trigger); or a per-instance apply-strategy mechanism lands, which would let SSA remain on for Postgres databases that do not use autoscaling.
