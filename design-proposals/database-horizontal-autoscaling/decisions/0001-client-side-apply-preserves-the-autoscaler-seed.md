# 0001. The autoscaler seed survives because the tenant HelmRelease applies client-side

- **Number:** `0001`
- **Date:** `2026-09-02`
- **Status:** Accepted
- **Deciders:** `@scooby87, @lllamnyp`
- **Proposal:** [`../README.md`](../README.md)
- **Decided in:** [`cozystack/community#66`](https://github.com/cozystack/community/pull/66)
- **Implemented in:** [`cozystack/cozystack#3954`](https://github.com/cozystack/cozystack/pull/3954) — open at the time this record landed; this header line tracks its state and is updated when it merges

## Context

The proposal's §3 committed to *omitting* `.spec.instances` from the rendered engine CR under active autoscaling. With the field absent from the manifest, Flux would neither set nor revert it, and the HPA — writing the CNPG `Cluster`'s `/scale` subresource — would be its sole writer. That was the whole ownership argument, and on paper it deleted the contested-field problem outright.

Building it against the current platform disproved that a chart-only omit is safe. Two facts were in play. First, the platform's helm-controller was on `v1.5.0` (`internal/fluxinstall/manifests/fluxcd.yaml`), which hardcodes `ForceConflicts = ServerSideApply` identically across install/upgrade/rollback (`internal/action/install.go:53`, same in `upgrade.go`/`rollback.go`) but does *not* share the apply-strategy default across them: `upgrade`/`rollback` default to `auto` (resolved by reading the previous release's `ApplyMethod`), and the install server-side default is itself gated behind the `UseHelm3Defaults` feature gate. So "defaults to server-side apply" holds exactly only for a *new* HelmRelease; a Postgres release predating v1.5.0 was already applying client-side on every upgrade — which is why the "reverted on every apply" failure never touched that population (the same split the last Consequences bullet notes from the other direction). For a new release, though, any field the chart *renders* is force-owned by Flux and reverted from the HPA's live value on every apply — and Flux performs an apply on every chart or values change, which every platform release triggers. Second, the omit handoff assumed the HPA already owned `.spec.instances` at the moment the field left the manifest; but an HPA claims the `/scale` field manager only when it actually writes (`rescale = desired != current`), so a cluster idle at its floor never writes, never owns the field, and the phase-2 omit prunes it — whereupon CNPG's CRD default (`instances: 1`) takes over and the quorum webhook rejects the cluster or standbys and their PVCs are shed. Closing that gap chart-only would need the runtime actor the design had deliberately removed.

A constant-seed alternative was therefore explored, and a reviewer ([@IvanHunters](https://github.com/cozystack/community/pull/66)) raised the objection that reopened the question: forcing client-side apply does not make a rendered constant a no-op, because Helm's three-way JSON merge computes its add-and-change delta from the *live* object, so an unchanged constant would still be re-asserted against a drifted live count. That objection is the reason this record exists.

## Decision

Under active autoscaling the chart renders `.spec.instances` as a constant seed `max(replicas, effectiveMin)` (never omitted), and the tenant HelmRelease applies **client-side**, forced per application by `release.cozystack.io/helm-server-side-apply: "false"` on the `ApplicationDefinition`. Under client-side apply helm-controller patches the CNPG `Cluster` — an unstructured/CRD object — from the previous-versus-new rendered manifest and, on the upgrade action any applying reconcile takes (an unchanged release short-circuits to `InSync` and runs no Helm action at all), does not consult live state (the two-way merge for unstructured objects), so the unchanged constant produces no patch and the value KEDA writes through `/scale` survives every reconcile. The one exception is the install-with-adoption recovery path, where the same forced client-side setting instead selects a three-way merge that *does* read live and rebases the seed; it is bounded and documented as a residual write path in Consequences below, not a steady-state behaviour.

## Why not the alternatives

- **Chart-only omit under active autoscaling (the proposal's own §3).** Lost on a structural fact, not a packaging detail: on helm-controller v1.5.0 a rendered field is force-owned under SSA and reverted, and the phase-2 omit prunes `.spec.instances` for any cluster idle at its floor (the HPA has not written `/scale`, so owns nothing), collapsing it to the CNPG default of 1. Both failure modes are unavoidable without a runtime writer the design removed. Verified live on dev9.
- **Constant seed under the platform-default server-side apply.** Same force-revert: SSA with `ForceConflicts` steals the rendered field back from `/scale` on every apply. Reproduced directly — a CRD grown out of band to 4 and re-applied via `helm upgrade --server-side --force-conflicts` with the chart rendering the lower constant reverted to the constant in one step.
- **Constant seed under client-side, accepting the reviewer's "three-way re-asserts from live" reading.** Refuted at the source. Helm v4's `createPatch` (`helm.sh/helm/v4 pkg/kube/client.go`) routes unstructured/CRD objects to a **two-way** `jsonpatch.CreateMergePatch(original, modified)` — previous rendered manifest against new, live never read — taking the three-way `CreateThreeWayJSONMergePatch(original, modified, current)` the objection quotes only when `threeWayMergeForUnstructured` is set, which helm-controller v1.5.0 never does (no reference anywhere in it). helm-controller v1.5.0 embeds v4.1.1 (`go.mod`), whose `createPatch` takes the identical two-way arm; confirmed empirically on Helm 4.0.4: a resource drifted to 4 out of band, then `helm upgrade --server-side=false` rendering the constant 2 *and* changing an unrelated field left `spec.instances` at 4 (only `--server-side --force-conflicts` reverted it).
- **Pinning `.spec.instances` via the scale subresource across the apply (the proposal's named fallback).** Rejected: it re-introduces a runtime writer of the CR's spec, which is exactly the property §3 set out to eliminate. Client-side apply achieves the same guarantee with no actor.

## Consequences

- A new platform knob: a per-`ApplicationDefinition` annotation (`release.cozystack.io/helm-server-side-apply`) threaded into `Install`/`Upgrade.ServerSideApply` on the emitted HelmRelease (`pkg/config`, `pkg/cmd/server/start.go`, `pkg/registry/apps/application/rest.go`). It is general, not postgres-specific.
- The annotation is **per-kind**, so client-side apply reaches *every* Postgres, not only autoscaled ones. That trades away, for Postgres specifically, the SSA benefit v1.5.0 introduced — misplaced chart fields becoming hard errors rather than silently dropped (`docs/changelogs/v1.5.0.md`). Accepted because Postgres shipped on client-side apply before v1.5.0 without issue; a per-instance apply strategy that keeps SSA on for non-autoscaled databases is a possible follow-up. This basis is Postgres-specific: the next engine on the ladder (MariaDB, §Scope) does not inherit it and must re-establish and re-justify the client-side-apply trade — or adopt the per-instance strategy — when its autoscaling lands.
- One residual write path remains under client-side too: the two-way patch propagates any change between the previous and new *manifest*, so anything that moves the rendered `.spec.instances` rebases it in that one reconcile. Three triggers, all bounded by the seed so none drops below the quorum floor or collapses to 1. Two stay inside the seed branch: a tenant edit to the seed's inputs (`replicas`, `autoscaling.minReplicas`, `quorum.maxSyncReplicas`), and — less obvious — a platform upgrade that changes how the seed renders (the `effectiveMin`/seed helper or a schema default), which rebases an HPA-grown count on the next apply with no tenant edit. The third leaves the seed branch: flipping an already-grown cluster into a staging mode (`transition` or `dryRun`) while `enabled` stays true renders the *static* `instances: {{ .Values.replicas }}`, **not** clamped to the floor (only CNPG's own quorum webhook backstops it), so an unstaged flip sheds the live count all the way down to `replicas`. All three carry the same mitigation — stage `.Values.replicas` to the live count before the change — documented as the floor-change caveat in `packages/apps/postgres/values.yaml` field comments (with a suspend-and-pin recipe) and in §Upgrade (covering the `transition` flow, the autoscaling-active chart bump, and the staging-mode flip).
- A second, much narrower path sits outside the two-way merge entirely: install-with-adoption. If a `Cluster` survives but its HelmRelease release-storage is lost (etcd recovery, namespace-secret cleanup, a Flux storage migration — and the postgres templates carry no `helm.sh/resource-policy: keep`, so an uninstall/reinstall remediation would take the `Cluster` with it and is excluded), the next reconcile runs a Helm `install`, not an `upgrade`. There `updateThreeWayMergeForUnstructured := TakeOwnership && !ServerSideApply` (`helm.sh/helm/v4@v4.1.1 pkg/action/install.go:503`) is **true today** (`TakeOwnership` defaults true, this design forces `ServerSideApply=false`), so Helm computes a three-way patch that reads live and rebases an HPA-grown `.spec.instances` to the seed in that one reinstall — bounded as the others (never below the floor, never a collapse to 1) but a real shrink of the grown set during recovery. Unlike the upgrade path it is not gated by any future flag flip — live today by design, which is why the steady-state invariant is stated for the upgrade path specifically. It has no in-band staging recipe (it fires on a recovery reinstall, not a tenant edit); the mitigation is to re-stage `.Values.replicas` to the intended live count once release storage is restored.
- A third path sits outside any patch — it re-creates the object from scratch: backup/restore. An in-place restore, or a restore into an existing autoscaling-active application, runs through `internal/backupcontroller/cnpgstrategy_controller.go`, whose `purgeExistingCluster` **deletes** the CNPG `Cluster` and its PVCs (`client.Delete`, not a patch) before the resumed HelmRelease re-creates it via `bootstrap.recovery`. With the live object gone, Helm's apply takes the `Create` arm (`helper.Get` → `NotFound`), so the fresh `Cluster` renders straight from the chart at the seed `max(replicas, effectiveMin)` — the floor, not the grown count. The restore controller is autoscaling-unaware (patches only `Bootstrap`/`Backup`, never reads `replicas`/`autoscaling`), and landed in main via [cozystack/cozystack#3959](https://github.com/cozystack/cozystack/pull/3959). Bounded as the others (never below the floor, never a collapse to 1), and the `ScaledObject`/HPA survive the purge, so the autoscaler re-grows to load once the restore catches up. Here the staging recipe is **inapplicable by construction** — the purge exists precisely to erase live state — so this is a conscious rebase-to-seed on restore, not a data-loss path.
- A fourth path is **operator-invoked, not automatic**, and named here so the residual-path list stays complete: setting `spec.upgrade.force: true` on the HelmRelease — the documented Flux remedy for an immutable-field upgrade error, which a CNPG `Cluster` can hit — sets helm-controller's `Upgrade.ForceReplace = Upgrade.Force` (`internal/action/upgrade.go`), which makes Helm apply the object through a full-object **replace** (`helper.Replace`, an HTTP PUT — *not* a two-way merge patch, and *not* a delete-and-recreate: same object, same UID) rather than the two-way patch the steady-state path uses. The replaced object renders `.spec.instances` from the seed, not the live count, so on every reconcile the flag stays set it rebases an HPA-grown count back to the seed — the same shrink the patch paths can cause, reached a different way (the PUT overwrites the whole spec rather than diffing one field, but the effect on `.spec.instances` is the same rebase-to-seed, not extra disruption). This path is reachable *because* this design forces client-side apply: Helm rejects `force` together with server-side apply outright (`helm.sh/helm/v4 pkg/kube/client.go` `Update` errors on `serverSideApply && forceReplace`), so under the platform's SSA default a forced upgrade would fail rather than replace. It is bounded by the seed like the others (never below the floor, never a collapse to 1); its only mitigation is to re-stage `.Values.replicas` to the live count first, or to clear the `force` flag once the immutable-field error is resolved. It is kept off the *Revisit if* trigger because it is an existing operator action, not a future SDK change.
- Behaviour no longer splits by install date. Because the annotation forces `Install.ServerSideApply=false` and `Upgrade.ServerSideApply=disabled` uniformly, both pre- and post-v1.5.0 Postgres releases apply client-side; there is no population that silently stayed on SSA.

## Revisit if

the embedded Helm SDK's *upgrade* action starts passing `ClientUpdateOptionThreeWayMergeForUnstructured` — the real lever, not any helm-controller setting (it exposes none, as established above). Verified against `helm.sh/helm/v4` v4.1.1: `pkg/action/upgrade.go` does *not* pass it, so it falls to its Go zero value (off) and the upgrade patch stays two-way for unstructured/CRD objects — what makes the steady-state no-op hold — while the sibling `pkg/action/install.go:503` *does* compute it (`i.TakeOwnership && !i.ServerSideApply`); the two actions are asymmetric today. If a future SDK made `upgrade.go` gain or pass `ClientUpdateOptionThreeWayMergeForUnstructured` like `install.go`, the upgrade-path patch would read live state and re-assert the constant, breaking the no-op on steady-state reconciles for *every* client-side release — the exact failure the reviewer described — arriving through an ordinary Flux/helm-controller image bump a maintainer watching "helm-controller settings" would not see; with no repeatable test holding this behaviour, this trigger is the only protection and must be diffed against v4.1.1 on the next SDK bump. (The install-with-adoption three-way read is separate: not this upgrade-path asymmetry, already live today by design through `install.go`, and handled as the bounded recovery caveat in Consequences, not a revisit trigger.) Or drift detection is turned on for these HelmReleases (`spec.driftDetection.mode: enabled`): it is `disabled` by default and the emitted HelmRelease never sets it, so it is unreachable today, but if the platform ever enabled it, helm-controller's drift correction re-applies the rendered manifest and would revert an HPA-grown `.spec.instances` to the seed — a second live-reading path, distinct from the upgrade-action asymmetry above, that a GitOps-hardening change could introduce without touching this design. Or a per-instance apply-strategy mechanism lands, which would let SSA remain on for Postgres databases that do not use autoscaling.
